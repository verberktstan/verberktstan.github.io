Bitten

2026 · A tiny bi-temporal, append-only database server in Babashka and SQLite.

  • Babashka
  • SQLite
  • EDN
  • TCP

View on GitHub

Most databases tell you what is true now. Bitten tracks two independent time axes for every fact:

  • Valid time: when the fact was true in the real world.
  • Transaction time: when the database learned about it.

That lets you ask questions like "what did we know about Alice on 1 June, as of the snapshot we had in September?" You get a deterministic answer even after retroactive corrections.

Design

Facts are never updated or deleted. Every change is a new row, and retractions are explicit. Audit history isn't a separate table you might forget to update: it's the storage model itself.

The whole thing is deliberately small. It's one SQLite table behind a newline-delimited EDN-over-TCP protocol, so any EDN-capable client can talk to it.

{:op :transact :records [{:db/entity "user/1" :user/name "Alice"}]}
{:op :query :e "user/1" :as-of-valid "2024-06-01"}

Why Babashka

It starts fast, needs no JVM warm-up and has SQLite access through a pod. A server you can read in one sitting, start in milliseconds and swap the storage underneath without touching the query model.
